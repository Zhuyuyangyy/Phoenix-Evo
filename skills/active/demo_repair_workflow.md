## When to Use
当任务涉及修复 demo、修复测试失败（test 跑不过）、修复演示脚本时，用最小复现→单点修复→全量验证三步走，而不是直接大改代码。

## Procedure
1. **最小复现**：找到 fail 的测试/命令，用最小参数、最少依赖复现问题
   - 失败命令：demo.py --arg1=x --arg2=y → 先用 demo.py 单参数跑
   - 测试失败：pytest tests/test_xxx.py::test_name -v → 先去掉 -v 和其他 flag 只看最小失败
2. **单点修复**：找到失败点后，只改那一个最小单元，不要同时改多个地方
   - 如果是函数签名问题：只修那一个函数
   - 如果是导入问题：只修那一个 import
   - 如果是数据问题：只修那一条数据
3. **全量验证**：修复后立即跑 demo/test，确认修复没有引入新问题
   - pytest 而不是 unittest（更详细的 traceback）
   - demo.py --help 或 demo.py --dry-run 先做烟雾测试
4. **回退准备**：修复前备份 git commit 或 /tmp/ 备份，修复出问题能一键回退
5. **回归测试**：用 git diff 或手动对比，确认修复的代码行数和影响的函数数量都是最小的

## Failure Cases
| 错误阶段 | 错误信息 | 修复策略 |
| -------- | -------- | -------- |
| 最小复现找不到根因 | 单参数跑通过但组合参数失败 | 逐步加参数，用二分法隔离，先加风险最高的参数 |
| 单点修复后 demo 通过但测试失败 | demo 和 test 的断言条件不一致 | 检查 test 和 demo 是否在验证同一行为，可能是测试用例本身写错了 |
| 修复引入新问题 | 修复了 A 功能的 bug 导致 B 功能损坏 | 立即回退到备份，用 git stash 或 /tmp 备份恢复 |
| 多次修复仍失败 | 修复→测试→再修复循环超过 3 次 | 停下来分析根因，可能是架构问题而非单点 bug，重新评估修复策略 |

## Safety Note
